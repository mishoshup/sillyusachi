## Oracle Findings

### Architecture Analysis

#### Why the Current Lenis Approach Is Broken

After reading all four relevant files (scroll-snap.js, +page.svelte, +layout.svelte, app.css), I found **five specific bugs** that together make scrolling completely broken:

##### Bug 1: Dual Snap Points Cause Locking (PRIMARY CAUSE)

Each section gets BOTH a `start` and `end` snap point via:
```
snap.addElement(section, { align: ['start', 'end'] })
```

With `type: 'lock'`, the user **cannot scroll freely** — every wheel tick or touch gesture locks onto the nearest snap point. Since each section has two snap points:
- Scrolling down from section 0 → locks to snap 0 (start)
- Next scroll → locks to snap 1 (end of same section) — **same position if section height ≈ viewport**
- Next scroll → finally reaches snap 2 (section 1 start)

This creates a **double-tap feel**: user scrolls twice but stays at the same position. When sections are taller than viewport, start and end points diverge, causing erratic jumps. The `lock` type with dual points makes scroll behavior fundamentally unpredictable.

##### Bug 2: wrapper === content Means Zero Scroll Delta

```
const lenis = new Lenis({
  wrapper,       // <main> element
  content: wrapper,  // SAME element
  ...
});
```

In Lenis v1, setting `wrapper` and `content` to the same element is problematic:
- Lenis cannot apply `transform: translateY()` to the element itself without displacing the viewport
- Scroll height calculation is unreliable when wrapper === content
- Svelte's `h-[100dvh]` on `<main>` further confuses dimension measurement

The correct Lenis pattern requires wrapper ≠ content, with content being a child wrapper div.

##### Bug 3: Layout overflow-hidden Creates Inherited Clip Chain

Layout div has `h-[100dvh] overflow-hidden` which clamps everything to viewport. The `<main>` child is `h-[100dvh]` inside it. While `<main>` doesn't overflow the layout div, the layout's `overflow-hidden` prevents `<main>` from establishing its own scroll context.

This forces the entire content area to be exactly one viewport — Lenis has nowhere to "scroll" to.

##### Bug 4: Section Height Measurement Mismatch

Sections use `min-h-[100dvh]` — actual height depends on content. Lenis + Snap calculates snap positions **at initialization** based on element offsets. If sections change height after render (images, fonts loading, dynamic content), snap points become **wrong**.

The `debounce: 500` with `resize()` listener helps with window resize but not content shifts.

##### Bug 5: RAF Loop + Svelte onMount Lifecycle

The RAF loop starts in `onMount`, but Lenis may take its first measurements **before** Svelte finishes laying out all sections. This gives Lenis a 0 or 100dvh scroll height on first frame, calculating impossible snap positions.

### Option A: Pure CSS scroll-snap ✅ RECOMMENDED

Aligns with CONTEXT.md decision.

#### Approach

Replace the JavaScript scroll system with CSS-native `scroll-snap`:

```css
/* On main scroll container */
main {
  overflow-y: scroll;
  scroll-snap-type: y proximity;
  height: 100dvh;
  scrollbar-width: none;
  -ms-overflow-style: none;
}
main::-webkit-scrollbar {
  display: none;
}

/* On each section */
section {
  scroll-snap-align: start;
  min-height: 100dvh;
}
```

Nav tracking via IntersectionObserver:
```javascript
const observer = new IntersectionObserver((entries) => {
  entries.forEach(entry => {
    if (entry.isIntersecting) currentPage = Number(entry.target.dataset.page);
  });
}, { threshold: 0.5 });
sections.forEach(s => observer.observe(s));
```

Programmatic scroll for nav buttons:
```javascript
sections[index].scrollIntoView({ behavior: 'smooth', block: 'start' });
```

#### How It Solves Each Bug

| Bug | Issue | CSS Fix |
|-----|-------|---------|
| 1 | Dual snap points lock | Single `scroll-snap-align: start` = one snap per section |
| 2 | wrapper === content | No wrapper/content concept — native overflow does the job |
| 3 | Layout overflow-hidden | Remove `overflow-hidden` from layout div (safe — overlays use fixed/absolute) |
| 4 | Section height changes | CSS scroll-snap dynamically adapts — no init timing issue |
| 5 | RAF lifecycle | No RAF — native scroll handles everything |

#### Architectural Change: Layout

The layout wrapper MUST lose `overflow-hidden`:

```diff
- <div class="h-[100dvh] overflow-hidden bg-[#080612] bg-cover bg-fixed">
+ <div class="h-[100dvh] bg-[#080612] bg-cover bg-fixed">
```

This is safe because:
- GlitterOverlay is fixed-positioned — unaffected by parent scroll
- Haze overlays are fixed-positioned — unaffected by parent scroll
- `<main>` controls its own scrollport via `overflow-y: scroll`

#### Risks

1. **Browser inconsistency**: `proximity` vs `mandatory` — `proximity` is safer for natural scrolling
2. **Scrollbar hiding**: Non-standard CSS, needs all vendor prefixes
3. **Nav tracking**: IntersectionObserver with `threshold: 0.5` is robust but needs testing
4. **No custom easing**: Native smooth scroll uses browser defaults. Acceptable trade-off.

### Option B: Hybrid CSS + JS (IntersectionObserver + CSS scroll-snap)

Nearly identical to Option A. The only difference is programmatic scroll uses:
```javascript
main.scrollTo({ top: sectionOffsetTop, behavior: 'smooth' });
```
instead of `scrollIntoView`.

**No meaningful difference** for this project. Option A or B both work.

### Option C: Fix Lenis (keep current approach)

#### Changes Required
1. **Layout**: Remove `overflow-hidden` from layout wrapper
2. **Lenis**: Proper wrapper/content separation — `<main>` as wrapper, inner div as content
3. **Snap points**: Change from `[start, end]` to single `start`
4. **Snap type**: Consider `mandatory` instead of `lock`
5. **Debounce**: Reduce from 500ms to 100ms

#### Risks
1. **Lenis v1.3.23 + Snap**: May have undiscovered bugs
2. **Bundle size**: ~17KB for something CSS does natively
3. **Maintenance burden**: Git log shows 3 prior attempts to fix scroll — this isn't isolated
4. **No advantage for 3-section page**: CSS scroll-snap provides identical UX

---

### Recommendation

**Option A (Pure CSS scroll-snap) — fully aligned with CONTEXT.md decision.**

Rationale:
1. Eliminates all 5 bugs in one clean sweep
2. Zero JS dependencies for scroll
3. Native browser scroll is battle-tested everywhere
4. Simplify codebase — delete scroll-snap.js, simplify +page.svelte
5. Future-proof — CSS scroll-snap has been widely supported since 2019
6. Content structure (3 sections, no sub-snapping) is ideal for CSS scroll-snap

The only real loss is Lenis custom easing, which is a reasonable trade-off for reliable scrolling.

### Architectural Decisions Needed

Already decided per CONTEXT.md:
1. ✅ Remove layout overflow-hidden
2. ✅ Single snap point per section (scroll-snap-align: start)
3. ✅ IntersectionObserver for nav tracking
4. ✅ Remove lenis package dependency
5. ✅ Delete scroll-snap.js
6. ✅ Cross-browser scrollbar hiding

### Implementation Order (Suggested)

2. Add CSS scroll-snap to `<main>` in `+page.svelte`
3. Add IntersectionObserver for nav tracking

# Librarian Findings

## CSS Scroll-Snap for Mixed-Height Sections

### Core CSS Properties
| Property | Role | Values for Our Use Case |
|----------|------|------------------------|
| `scroll-snap-type` | Container-level — defines snap axis & strictness | `y proximity` — **proximity** is key for mixed-height sections |
| `scroll-snap-align` | Child-level — defines snap position | `start` on all sections; tall sections get `min-height: 100dvh` with `scroll-snap-align: start` |
| `scroll-snap-stop` | Prevents skipping snap positions | `normal` (default) — **avoid `always`** with mixed heights (conflicts) |
| `scroll-padding` | Container-level offset | `40px` or safe area insets to account for fixed elements |
| `scroll-margin` | Child-level outset | Optional per-section fine-tuning |

### Handling Tall Sections (> Viewport)
The **key insight** from the spec is in [Scroll Snap Overflow Handling](https://drafts.csswg.org/css-scroll-snap/#snap-overflow):

> "If the element is larger than the scroll container, the user should be able to scroll freely within that element, only snapping at its edges."

For sections taller than the viewport:
- **Use `proximity`** instead of `mandatory` — mandatory + overflow content = user **cannot** reach middle content (spec calls this out as a warning: "Never use mandatory if content inside one of your child elements will overflow the parent container")
- **Use `min-height: 100dvh`** for tall sections — allows natural content expansion
- **`scroll-snap-align: start`** — snaps top of each section to top of viewport; when a tall section overflows, the browser auto-allows free scrolling within it
- **Sentinel approach** (fallback): inject a 1px sentinel div at the bottom of tall sections with `scroll-snap-align: end` to ensure next section engages after full scroll-through — NOT needed with proximity + proper overflow handling

### Browser Compatibility
- **CSS Scroll Snap Level 1**: Supported in all modern browsers since ~2020
  - Chrome 69+, Firefox 68+, Safari 13+, Edge 79+
  - ~97% global support (CanIUse)
- **`scroll-snap-stop`**: Chrome 75+, Firefox 103+, Safari 15+
- **`scroll-padding`**: Chrome 69+, Firefox 68+, Safari 14.1+
- **`scroll-margin`**: Chrome 69+, Firefox 68+, Safari 11+
- **`100dvh`** (dynamic viewport): Chrome 108+, Safari 15.4+, Firefox 101+ — fine for modern
- No feature detection needed for our target browsers; but if desired:
  ```css
  @supports (scroll-snap-align: start) {
    /* CSS scroll-snap styles here */
  }
  ```

### Common Pitfalls
1. **`overflow: hidden` on parent** — breaks scroll entirely (already identified in CONTEXT.md)
2. **`mandatory` + tall content** — makes mid-content inaccessible (MDN explicitly warns)
3. **`scroll-snap-stop: always` on proximity** — forces snap even when user wants to overscroll through a tall section (current code had this issue)
4. **Scroll-snap + overscroll-behavior** — orthogonal, not conflicting
5. **`touch-action: pan-y` on sections** — can interfere with snap precision; set only on the scroll container
6. **Missing container height** — scroll-snap requires a defined `overflow` + size on the scroll container
7. **`h-[100dvh]` on tall sections** — clips content; use `min-h-[100dvh]` instead (already applied in fix)

### Current Project Status (Good)
The existing setup already uses:
- `scroll-snap-type: y proximity` ✓
- `min-h-[100dvh]` on all sections ✓
- `scroll-snap-align: start` on sections ✓
- `scrollbar-width: none` + `::-webkit-scrollbar { display: none }` ✓
- **NO** `scroll-snap-stop: always` ✓ (was removed during fix)
- Scroll container with `overflow-y-auto` ✓

### Recommendation
Keep **pure CSS scroll-snap with `y proximity`**. The Lenis approach was overengineered — CSS scroll-snap natively handles mixed heights via the overflow rule in the spec. The current code has this structure right after the scroll-v2 fix. Main verification needed:
1. Does the scroll container properly allow overflow in tall sections?
2. Does the CommissionInfo section flow naturally without clipping?
3. Does snap behavior feel smooth with `proximity` on desktop?

## Scroll-related Testing Approaches

### What Works in Vitest + JSDOM
- **DOM structure**: querying rendered HTML, checking classes, attributes, text content
- **Mocking DOM APIs**: `document.createElement`, `Element.prototype.getBoundingClientRect`
- **Event dispatch**: `dispatchEvent(new Event('scroll'))`
- **Element properties**: `scrollTop`, `scrollHeight`, `clientHeight`, `offsetTop`
- **Assertions**: checking class names, style properties, child elements

### Mocking IntersectionObserver
```typescript
import { vi } from 'vitest';

// Global mock for IntersectionObserver
const IntersectionObserverMock = vi.fn((callback) => ({
  observe: vi.fn(),
  unobserve: vi.fn(),
  disconnect: vi.fn(),
}));

vi.stubGlobal('IntersectionObserver', IntersectionObserverMock);

// After tests
vi.unstubAllGlobals();
```

For testing that the observer fires with correct entries:
```typescript
it('calls onPageChange when section intersects', () => {
  let observerCallback = null;
  
  vi.stubGlobal('IntersectionObserver', vi.fn((callback) => {
    observerCallback = callback;
    return {
      observe: vi.fn(),
      unobserve: vi.fn(),
      disconnect: vi.fn(),
    };
  }));
  
  const onPageChange = vi.fn();
  setupScrollSnap(container, onPageChange);
  
  // Simulate intersection
  observerCallback(
    [{ isIntersecting: true, target: sections[1] }],
    { target: container }
  );
  
  expect(onPageChange).toHaveBeenCalledWith(1);
});
```

### Testing Scroll-Snap in JSDOM (Limitations)
JSDOM **does not implement**:
- Actual scrolling mechanics
- CSS scroll-snap behavior (no layout engine)
- Element visibility / viewport intersection (no visual rendering)
- `scroll-snap-type`, `scroll-snap-align` — these are pure CSS, no-op in JSDOM
- `getComputedStyle` does NOT reflect computed scroll snap values properly

**What you CAN test:**
- The DOM structure that scroll-snap relies on (correct classes, data attributes, style tags)
- That sections have the correct CSS classes (`snap-fit`, `snap-tall`)
- That inline styles or computed CSS align with expectations
- Mock scroll events and verify event handler behavior
- That height detection logic works correctly

**What you CANNOT test:**
- Whether scroll-snap actually snaps to the right position
- Whether snapping feels smooth
- Whether `proximity` triggers at the right distance
- End-to-end scroll flow

**Recommendation:**
- **Unit tests**: Logic in `scroll.js` (extract pure functions for height classification, sentinel injection)
- **Component tests**: Rendering, class assignment, prop handling via `@testing-library/svelte`
- **E2E tests**: Use Playwright for actual scroll behavior testing (separate setup)
- Vitest browser mode with Playwright can test actual scroll snap behavior in a real browser

### Vitest Browser Mode (For actual scroll testing)
If you want to test actual scroll-snap behavior programmatically, use Vitest + Browser Mode which runs tests in real Chromium:

```typescript
import { defineConfig } from 'vitest/config';
import { svelte } from '@sveltejs/vite-plugin-svelte';
import { playwright } from '@vitest/browser-playwright';

export default defineConfig({
  plugins: [svelte()],
  test: {
    browser: {
      enabled: true,
      provider: playwright(),
      instances: [{ browser: 'chromium' }],
    },
  },
});
```

This gives you `toBeInViewport()` assertions, real scroll, real CSS scroll-snap, real IntersectionObserver.

### Testing Strategy for This Project

| Layer | Tool | What to Test |
|-------|------|-------------|
| **Logic** (scroll.js) | Vitest + jsdom | Height classification, sentinel injection, observer setup |
| **Components** (CommissionInfo, AboutMe) | Vitest + jsdom + `@testing-library/svelte` | Rendering, props, derived state, class logic |
